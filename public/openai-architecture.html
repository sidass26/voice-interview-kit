Research Bot — How It Works
📋
Trigger
Intake form submitted → POST /api/sessions
Immediately after the employee submits their trip details, the server fires runDestinationResearch() asynchronously. The session status is set to researching. The interview start button stays disabled until this completes.
🔍
API Call — OpenAI Responses API
gpt-4.1 + web_search_preview tool
Uses openai.responses.create() — NOT chat.completions.create(). The Responses API is a different endpoint that supports live web tool use. The model autonomously decides when to trigger web searches during its response.
openai.responses.create({ model: 'gpt-4.1', tools: [{ type: 'web_search_preview' }], instructions: 'Focus on Reddit discussions for authentic opinions.', input: buildResearchPrompt(destination, cities, tripType, purpose), })
🌐
Web Searches Performed
Reddit + travel forums searched automatically
The prompt instructs the model to search for 8 specific query patterns:
• "What do people wish they knew before visiting destination?"
• "Best food in city" discussions
• "destination budget breakdown" threads
• "Mistakes I made in destination" posts
• Overrated vs underrated takes
The model issues multiple web searches and synthesises the results — it never just returns URLs.
📦
Output — Structured JSON
Saved to research_snapshots table
The model returns a strict JSON object (no markdown wrapping). The schema covers 9 topic buckets, unique destination angles, real Reddit questions people ask, and per-city breakdowns.
// DestinationResearch — what gets stored in research_snapshots.research_data { "destination": "Malaysia — Kuala Lumpur, Langkawi", "summary": "2-3 sentence overview of interview angles", "bucketHints": { "food": { "hints": ["Must-try nasi lemak variants", "Mamak stalls vs hawker centres"] }, "logistics": { "hints": ["Grab vs Myrapido debate", "Langkawi: MUST rent a car"] }, "budget": { "hints": ["Budget: $40–60/day, Mid: $100–150/day"] }, "mistakes": { "hints": ["Not renting car in Langkawi", "Skipping Batu Caves dress code info"] }, "disappointments": { "hints": ["Petronas towers: exterior > interior"] }, // + highlights, trip_overview, restaurants, practical_tips }, "uniqueAngles": ["KL vs Singapore comparison", "Langkawi as duty-free island"], "redditQuestions": ["Is Malaysia safe for solo female travel?", "How much cash to bring?"], "cityResearch": { "Kuala Lumpur": { "food": [...], "activities": [...], "tips": [...] }, "Langkawi": { "food": [...], "activities": [...], "tips": [...] } } }
The Research → Interview Handover
Research Phase
gpt-4.1 + Web Search
Async job fires after intake. Stores structured JSON in research_snapshots. Session status: researching → ready.

Interview is locked until status = ready. The interview page polls /api/sessions/[id]/research every 3 seconds.
→
Token Creation — The Handover Moment
GET /api/sessions/[id]/realtime
When the employee clicks Start Interview, the browser calls this server route. The server:
1. Fetches intake_responses from DB
2. Fetches research_snapshots from DB
3. Calls buildInterviewInstructions(intake, research)
4. POSTs to openai.com/v1/realtime/sessions with the instructions baked in
5. Returns an ephemeral token to the browser
6. Browser connects directly to OpenAI via WebRTC
buildInterviewInstructions() instruction-builder.ts
  • 1
    Persona — buildInterviewerPersona(destination, cities)
    Frames the bot as a colleague who "has been dying to visit" that specific place. Destination-aware, not generic.
  • 2
    Intake context — buildIntakeContext(intake)
    Injects: employee name, trip duration, cities visited, travel purpose, number of travelers, day-by-day itinerary.
  • 3
    Itinerary flow — buildItineraryContext(itinerary)
    The bot gets the day-by-day breakdown so it can ask "so Day 3 you were in Langkawi — what did you do?"
  • 4
    Research hints — buildResearchContext(research)
    All 9 bucket hints + city research + Reddit questions injected here. If research is missing, fallback text used.
  • 5
    Topic tracking rules — buildTopicTrackingInstructions()
    Rules for which topics are mandatory vs optional, and when to move on vs dig deeper.
How research appears in the prompt baked-in context

Voice Interview — How It Works in Practice
WebRTC Architecture No server in audio path
  • 1
    Browser fetches ephemeral token from /api/realtime (valid ~60s)
  • 2
    Browser opens WebRTC peer connection directly to api.openai.com/v1/realtime — audio never touches your server
  • 3
    Server VAD (Voice Activity Detection) at OpenAI detects speech automatically — no push-to-talk
  • 4
    Two transcript streams:
    • Bot speech: response.audio_transcript.done events
    • User speech: conversation.item.input_audio_transcription.completed events (requires input_audio_transcription: { model: 'gpt-4o-mini-transcribe' })
  • 5
    Browser PATCHes transcript entries to /api/sessions/[id] as they arrive
  • 6
    After interview ends, client POSTs to /api/sessions/[id]/process → pipeline triggers
5-Phase Interview Structure topic-tracker.ts
Phase 1
Trip Overview
Who went, how long, what type of trip. Sets the context. Bot uses intake data — never re-asks what was already collected.
Phase 2
Day-by-day walk-through
Bot follows the itinerary structure. Asks about each city in order. Uses city-specific research hints here.
Uses cityResearch[city].food, activities, tips from research JSON
Phase 3
Cross-cutting themes
Budget totals, biggest mistake, hidden gem, what they'd do differently.
Uses bucketHints.budget + bucketHints.mistakes from research JSON
Phase 4
Research rapid fire
Bot uses the Reddit questions from research as a rapid-fire round: "People on Reddit constantly ask — is Malaysia worth it vs Thailand? What would you say?"
Uses redditQuestions + uniqueAngles from research JSON
Phase 5
Close
Final advice, one-sentence summary, who they'd recommend this trip to.
Post-Interview Pipeline — 5 Steps

gpt-4.1
Polishes raw WebRTC transcript entries into readable dialogue. Fixes filler words, stutters, incomplete sentences.
02
Extract Data
gpt-4.1
Pulls structured facts (highlights, food, restaurants, budget, per-day breakdown). Every fact must cite a verbatim quote — prevents hallucination.
03

gpt-4.1
Writes first-person travel article from extracted data. Uses the extracted JSON, not the raw transcript — clean facts only.

Deterministic

05
Store
Supabase
Versioned article draft + payload saved to DB. Session status → completed. Old versions kept (never deleted).

Critical Design Decisions
Research blocks interview start — intentional
The "Start Interview" button is disabled until research_snapshots has a row for this session. The interview page polls /api/sessions/[id]/research every 3 seconds. This guarantees the research context is baked into the system prompt from question 1.
Without this: the interview started in parallel with research, sometimes research wasn't ready, the bot asked generic questions with no destination knowledge.
input_audio_transcription: { model: 'gpt-4o-mini-transcribe' } — must not be removed
Without this field in the Realtime session config, OpenAI never fires conversation.item.input_audio_transcription.completed events. Only the bot's side of the conversation gets transcribed. The user's entire side is missing.
Without this: the extraction model saw only bot questions, inferred user answers from context (bot asked "did you try nasi lemak?" → extractor assumed yes). Every fact was hallucinated. This was discovered after multiple failed articles.
Evidence log in extraction — anti-hallucination guard
Every extracted fact must include _evidenceLog: "exact verbatim quote from interviewee". The extraction prompt explicitly says: if no quote supports it, the field must be null.
Without this: bot asking "did you enjoy the spice market?" was treated as evidence the user visited it. The extractor inferred highlights from interviewer questions, not answers.
Responses API vs Chat Completions API — different endpoints
openai.responses.create() is used for research — NOT openai.chat.completions.create(). Only the Responses API supports web_search_preview tool use. These are different OpenAI endpoints.
Swapping to chat completions breaks web search entirely — the tool field is silently ignored.
No server-side WebRTC — server is not in the audio path
The server only creates an ephemeral token. The browser connects directly to OpenAI Realtime via WebRTC. Audio latency is minimised. If the browser tab closes mid-interview, partial transcript is preserved (PATCHed incrementally).
Server-side audio relay would add ~200–400ms latency. For a 15-min conversation this compounds to a noticeably laggy experience.
Model Usage Summary
Models used
  • gpt-4.1
    Research (Responses API + web_search_preview) + Transcript cleaning + Extraction + Article generation
  • gpt-4o-realtime
    Live voice interview — handles speech-to-speech in real time. Persona + all context baked into system prompt at token creation time.
  • gpt-4o-mini-transcribe
    User speech transcription — runs alongside the Realtime model to capture the interviewee's side of the conversation.
API surfaces used
  • A
    Responses API — openai.responses.create()
    Research only. Supports tool use (web search). Different endpoint from chat completions.
  • B
    Chat Completions API — openai.chat.completions.create()
    Transcript cleaning, extraction, article generation. Standard text-in text-out.
  • C
    Realtime API (WebRTC) — openai.com/v1/realtime/sessions
    Token creation on server. WebRTC connection from browser. Audio streamed directly to OpenAI.
